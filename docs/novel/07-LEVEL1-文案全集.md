# LEVEL 1《幽灵订单》· 文案全集（策划 / 文案向）

> **文档用途**：本关**所有玩家可见文本**的唯一来源。程序按 `logKey` 取用，不得在代码里硬编码文案。
> **配套文档**：`06-LEVEL1-实现规格.md`（逻辑）、`08-数值表与平衡模型.md`（数值）

---

## 0. 文案风格约定

| 类别 | 语气 | 禁忌 |
|---|---|---|
| **系统提示** | 客观、冷静、只报事实 | 不用感叹号，不做价值判断 |
| **卡牌描述** | 简短、口语、像同事在说话 | 不写技术名词解释 |
| **证据文本** | **像真的监控界面**。有数字、有时间戳、有单位 | 不写"这说明……"——推理是玩家的事 |
| **老赵台词** | 损、准、有温度 | 不说教 |
| **结算文本** | 克制。陈述结果，不表扬也不责骂 | 不写"恭喜通关！" |

**总原则**：**游戏从不告诉玩家"你做得对"或"你做得错"。它只把结果摆出来。**

### 2.7 `C_UPSTREAM` 查看上游调用

```
卡面名：      查看上游调用
卡面描述：     看看是谁在反复敲门。
悬停详情：     需要先做链路追踪。
             耗时 2 分钟 · 精力 1 · 只能查 1 次
```

**执行反馈 `upstream.retry`** ★ 关键正反馈

```
上游调用方配置：

  超时阈值：    500 ms
  重试策略：    固定间隔
  最大重试次数： 3

  ⚠ 未配置幂等键

也就是说：

  上游等了 500 毫秒，认为失败，重发一次。
  但订单服务其实成功了。
  两次请求的 requestId 不同——因为 requestId 是上游生成的。
  订单服务只检查 requestId 有没有处理过。

  所以两次都通过了。

  ┌────────────────────────────────┐
  │  根因已确认                     │
  │  上游超时重试 + 订单服务无幂等保护 │
  └────────────────────────────────┘
```

**产出证据 E5 · 置位 `rootCauseConfirmed`**

> **实现提示**：此文本出现时应播放明显的正反馈音效（clair de lune 式的单音上行），并让整个界面短暂地"亮"一下。这是本关最爽的一刻，必须给足。

### 5.1.1 评级判定块（`rankNote`）

**只在评级被"封顶"或"降级"时显示。** S / A 级不显示此块——它们的评级直接由影响值决定，无需解释。

| 触发条件 | 判定块内容 |
|---|---|
| `restartCount > 0` 且 影响值本可评 A 及以上 | 「影响值 X → 本应评为 A ／ 重启次数 N → 评级封顶为 B」 |
| `overclocked` | 「影响值 X → 本应评为 {原评级} ／ 视界超频 → 评级降为 {最终评级}」 |
| 两者同时 | 两条并列显示，并注明「两项均适用」 |

**这个块解决的是一个真实的理解障碍**：重启路径的影响值（31.4）**低于**标准解（44.0），但评级更差。没有这行说明，玩家会认为评分系统坏了。

**实现要求**：判定块必须显示**未封顶前的原始评级**，让玩家清楚看到"我本可以拿 A，是重启把它降到了 B"。这个落差就是教学。

复盘 · 幂等性

问题的本质不是"订单重复了"，
是"同一个请求被处理了两次，而系统认不出来"。

上游超时后重试，这是**正确的**行为。
订单服务两次都成功，也是**正确的**行为。

错的只有一件事：
订单服务没有能力识别"这两个请求其实是同一件事"。

解法叫「幂等」——同一个操作执行一次和执行十次，
结果必须相同。

实现幂等的三种常见方式：
  · 唯一索引（数据库层兜底，最可靠）
  · 状态机（只允许特定状态流转）
  · 去重表 / Redis 标记（性能好，但要处理过期）

你选择了唯一索引。这是最稳的那一种。
