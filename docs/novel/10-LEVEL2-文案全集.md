## 0. 本关的语气变化

LEVEL 1 是**白天的小事故**：一个新人、一个老油条、一间会议室。
LEVEL 2 是**大促的零点**：全员在岗、流量洪峰、CEO 在看大盘。

| 维度 | LEVEL 1 | LEVEL 2 |
|---|---|---|
| 时间 | 早上九点 | **深夜零点** |
| 在场人数 | 3–5 人 | 全组 + 运营 + 总监 |
| 系统状态 | 局部异常 | **全线过载** |
| 文案基调 | 略带荒诞的职场喜剧 | **紧绷、克制、倒计时感** |
| 老赵 | 贫嘴 | 话变少了 |

> **老赵在本关话变少是刻意的。** 他在 LEVEL 1 负责吐槽，在 LEVEL 2 负责沉默——因为这次是真的严重。玩家应该感觉到气氛变了。

### 2.4 `C_TTL` 检查过期时间配置 ★★ 关键

  sku:1001:stock      TTL = 3600s
  sku:1002:stock      TTL = 3600s

  promo:1109:list     TTL = 3600s

  23:01 写入的那一批，会在 **00:01** 同时过期。

  零点整，大促开始。
  缓存，也刚好在那个时候，集体到期。

  ┌────────────────────────────────────┐
  │  根因已确认                          │
  │  缓存 TTL 未加随机值，批量同时过期     │
  └────────────────────────────────────┘

### 2.5 `C_DIFF` 比对变更 ⚠️ 假线索

**执行反馈 `diff.found`**

```

  23:00  发布  promo-service v2.14.0
         「大促活动配置」
         变更人：李工

有变更。

就在 3 小时前。
```

**产出证据 E5**

> **这条线索是刻意设计的误导。** 它看起来完全合理——"出事前有发布"，这是 LEVEL 1 教的第一个直觉。
>
> 但这次发布改的是**活动配置**，和缓存的 TTL 无关。玩家如果据此去回滚，会浪费 4 分钟。
>
> **LEVEL 1 教你"出事先看变更"。LEVEL 2 教你"变更不等于根因"。**

```

> **注意文案重点**：限流**没有改善缓存**，它只是让连接池退回了安全区。
> 这是本关最重要的认知——**你不需要修好缓存，你只需要让连接池不满。**

卡面描述：     老办法。

**执行反馈 `restart.useless`**

```
[00:19:02] 正在重启 12 个实例...

[00:19:31] 实例启动完成
[00:19:32] 健康检查通过
[00:19:33] 全部实例重新接入流量

  缓存命中率：  12%（**没变**）
  连接池：      50/50（**还是满的**）
  数据库健康度： **继续下降**

重启没有用。

Redis 里的数据不在你的应用里。
那些过期的 Key，重启一万次也还是过期的。

而 12 个实例同时重新接入流量——
数据库在那一瞬间，挨了更重的一下。
```

### 6.1 S 级

────────────────────────────

老赵：
「加随机值。」
「这么简单的事，三年没人干。」

────────────────────────────

复盘 · 缓存雪崩

缓存雪崩不是"缓存坏了"。
是"缓存**同时**坏了"。

单个 Key 过期，只是少了一条缓存。
一万个 Key 在同一秒过期，
就是一万个请求同时砸向数据库。

而数据库只有 50 个连接。

三种缓存故障，请分清楚：

  · 穿透 —— 查一个**根本不存在**的数据，
            每次都绕过缓存打到数据库
  · 击穿 —— 一个**热点 Key** 过期，
            所有请求同时去重建它
  · 雪崩 —— **大量 Key 同时过期**，
            数据库瞬间被打满

你遇到的是雪崩。

解法有三种，你用了最根本的那一种：

  1. 过期时间加随机值（你做的）
  2. 多级缓存
  3. 缓存预热 + 永不过期 + 后台更新

第 1 种最简单，也最有效。
一行代码的事。
```

复盘 · 重启解决不了的事

你重启了服务。

重启在 LEVEL 1 里是有代价的，但它至少"有效"——
它清空了内存状态，故障强度确实降下来了。

这一次不一样。

Redis 不在你的应用进程里。
它是一个**独立的、分布式的**服务。
你重启一万次应用，那些过期的 Key 还是过期的。

而且，12 个实例同时重启、同时重新接入流量，
数据库在那一瞬间挨了更重的一下。

这是运维要记住的一句话：

  **重启只对"进程内状态"有效。**
  **对进程外的依赖，重启是无效的，甚至是有害的。**

```
【 F 】

────────────────────────────

复盘 · 你做错了什么

  扩容          → 连接池从 44/50 变成 50/50
                 数据库从"还有 28 分钟"变成"还有 15 分钟"

这不是运气不好。

────────────────────────────

复盘 · 为什么扩容会加速崩溃

你的直觉是：系统扛不住 → 加机器。

但数据库的连接数是**固定的**。
50 个连接，不管你前面有多少台应用服务器。

扩容做的事，不是让系统更能扛，
而是**让更多的请求同时挤向那 50 扇门**。

所以：

  · 数据库 CPU 更高了
  · 连接等待更长了
  · 连接池更快打满
  · **数据库死得更快了**

什么时候该扩容？
  当瓶颈在**应用层**的时候。

什么时候不该扩容？
  当瓶颈在**下游依赖**的时候——
  数据库、缓存、第三方接口。

**扩容只能解决"自己不够用"的问题。**
**它解决不了"别人不够用"的问题。**
**而且会让后者更糟。**
```
