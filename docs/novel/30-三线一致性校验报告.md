# 《代码视界》三线一致性校验报告

> **校验对象**：设定集 §3「视觉法则」的 48 条技术映射，在小说 / 漫剧 / 游戏三条线中的使用情况
> **校验工具**：`tools/audit-cross-line.ps1`（关键词匹配，可重跑）
> **结论摘要**：**19 条（40%）从未被任何一条线使用**；**8 条只在一线出现**，存在改编断层风险

---

## 一、方法说明与局限

### 1.1 方法

对设定集 §3.1 / §3.2 / §3.3 的 48 条映射，逐条提取关键词（如「金库」「二十个」「收尸人」），在三线的正文文件中做正则匹配。

- **小说线** = `13-` ~ `21-`（正文，不含细纲）
- **漫剧线** = `23-` ~ `28-`（分镜脚本）
- **游戏线** = `06-` ~ `11-`、`29-`（关卡规格）

### 1.2 局限（重要）

**关键词匹配有假阴性。** 抽查验证：

| 条目 | 关键词 | 小说中实际出现 | 判定 |
|---|---|---|---|
| GC 垃圾回收 | 收尸人 / 麻袋 | 「黑色的袋子」1 次 | **假阴性**——小说写了场景，但没用这个词 |
| 链路追踪 | 红线 | 「链路追踪」1 次 | **假阴性**——用了术语，没用视觉词 |
| 慢 SQL | 慢 SQL | 0 次 | 真阴性 |
| 脑裂 | 脑裂 | 0 次 | 真阴性 |

**所以本报告的「未使用」应理解为「未使用该映射的视觉语言」，不等于「完全没写这个概念」。**

## 二、校验结果

### 2.1 总体数据

| 指标 | 数值 |
|---|---|
| 映射条目总数 | **48** |
| 小说使用 | **20 条（42%）** |
| 漫剧使用 | **20 条（42%）** |
| 游戏使用 | **15 条（31%）** |
| 三线全覆盖 | **5 条** |
| 两线使用 | 16 条 |
| 单线使用 | 8 条 |
| **完全未用** | **19 条（40%）** |

### 2.2 三线全覆盖的 5 条

这 5 条是本 IP 视觉体系的**真正地基**：

| 条目 | 映射 |
|---|---|
| 数据库连接池 | 金库的门，只有 N 扇 |
| 幂等 | 城门守卫只认第一次的印章 |
| 限流 | 令牌闸机，一秒只放 N 个人 |
| 回滚 | 时光倒流——但只能倒回上一次快照 |
| 灰度发布 | 只开一条街的新路，看有没有人摔跤 |

> **注意**：这 5 条里有 3 条（连接池、幂等、限流）直接来自第一卷的核心技术副本。**这说明三线共用设定的设计是成立的**——只要某个技术点成为剧情核心，它就会自然渗透到三条线。

## 三、发现一：40% 未使用——但要分三类看

19 条未使用条目不能一概而论。按「是否属于第一卷的技术范围」分类：

### A 类 · 属于后续卷，本卷未用是正常的（13 条）

| 条目 | 归属卷 | 依据 |
|---|---|---|
| 单体应用 | 卷六《祖传老宅》 | 单体拆微服务 |
| 服务注册中心 | 卷四 / 卷六 | 微服务治理 |
| 布隆过滤器 | 卷二《雪崩》 | 缓存穿透的对策 |
| 消息积压 | 卷二 / 卷四 | MQ 相关 |
| 服务雪崩 | 卷二《雪崩》 | 卷名即此 |
| 主从延迟 | 卷四《两个城邦》 | 数据一致性 |
| 脑裂 | 卷五《死锁之城》 | 分布式锁与 CAP |
| 分布式事务 | 卷一后半 / 卷四 | — |
| 线程饥饿 | 通用 | 线程池的邻居概念 |
| 忙等待（自旋） | 通用 | 同上 |
| 单例 | 通用 | 设计模式 |
| 代理模式 | 通用 | 设计模式 |
| Git 冲突 / CI/CD | 通用 | 工程实践 |

**结论：这 13 条不是缺陷，是资产。** 它们是为第二至第七卷预写的视觉语言，**现在就应该保留在设定集里**。

### B 类 · 属于第一卷，但确实没用上（3 条）★ 真实缺口

| 条目 | 为什么说它是缺口 |
|---|---|
| **服务调用链** | 第一卷第五幕的核心就是「一笔订单跨三个服务」。**这段剧情在小说和漫剧里都是用文字讲的，没有用视觉语言** |
| **消息队列** | 第 24 章讲了「本地消息表」，但视界里从未出现过传送带或运河 |
| **分布式事务** | 「跨服务幂等」本质上就是分布式事务的入门。设定集里有「多个城主同时签字」的画面，三线都没用 |

**这三条是真正的「设定写了但没用」——而且它们恰好都落在第一卷的技术范围内。**

> **建议**：在第二卷补上。或者更彻底一点——**在 EP32（程叙讲三个服务那段）加一个「城主签字」的视觉插入**，成本很低，收益是把第一卷最重要的技术段落视觉化。

### C 类 · 通用概念，可用可不用（3 条）

慢 SQL、全表扫描、缺索引。这三个是数据库性能问题的经典三件套，但第一卷的剧情不涉及。

**建议：保留在设定集，等哪一卷用到再说。**

## 四、发现二：8 条单线条目 = 改编断层风险

这是**比"未使用"更值得警惕的问题**。

| 条目 | 出现在 | 断层风险 |
|---|---|---|
| **GC 垃圾回收（收尸人）** | 仅漫剧 | **小说写了场景但没命名，游戏完全没有**——第三卷的核心 Boss，现在只有漫剧有视觉 |
| **内存泄漏** | 仅游戏 | 第三卷的核心机制，小说和漫剧都没有视觉 |
| **OOM** | 仅游戏 | 同上 |
| **熔断** | 仅游戏 | 第二卷的核心卡牌，小说和漫剧没有视觉 |
| **缓存击穿** | 仅游戏 | 第二卷的机制 |
| **链路追踪** | 仅游戏 | 小说第 11 章用过这个概念 |
| **观察者模式** | 仅漫剧 | 设计模式，通用 |
| **技术债** | 仅小说 | 漫剧和游戏都没有对应视觉 |

### 4.1 最严重的一条：收尸人

**收尸人是第三卷《静止之城》的核心形象**（GC = 巡街的收尸人，STW = 全城静止）。

现状：
- **漫剧**：EP10 有完整镜头（拖着黑袋子，沿街捡东西）
- **小说**：第 10 章写了这个场景（「它拖着一个东西。一个黑色的袋子。」），但**从头到尾没有说出"收尸人"这个词**
- **游戏**：完全没有

> **这其实是刻意的**——小说里不命名，是为了给第三卷留揭示空间。
>
> **但游戏完全没有，是真缺口。** LEVEL 3《静止之城》的整个视觉核心就是它，而 `29-LEVEL3` 文档里只写了「Full GC 停顿」，**没有写收尸人**。

**建议：给 LEVEL 3 补一节「视界呈现」，把收尸人和全城静止的视觉写进游戏规格。** 这是三线共用设定最该落地的地方。

## 五、发现三：三线各自的视觉覆盖率

| 线 | 覆盖率 | 评价 |
|---|---|---|
| 小说 | 42% | 合理。小说靠文字叙事，不需要每个概念都有视觉 |
| 漫剧 | 42% | **偏低**。漫剧是视觉产品，覆盖率应该更高 |
| 游戏 | 31% | **偏低**。游戏关卡的技术可视化是核心卖点 |

### 5.1 为什么漫剧和游戏偏低

**因为这两条线只覆盖了第一卷。**

- 漫剧 40 集 = 第一卷
- 游戏 3 关 = 第一卷的三个技术副本

而设定集 §3 是为**全七卷**写的。

**所以 31%–42% 这个数字本身不是问题——问题是"本卷范围内该用的没用"。**

按这个标准重新算：

| 线 | 第一卷范围内的映射条目 | 已使用 | 覆盖率 |
|---|---|---|---|
| 小说 | 约 20 条 | 20 条 | **接近 100%** |
| 漫剧 | 约 20 条 | 20 条 | **接近 100%** |
| 游戏 | 约 12 条 | 15 条 | **超出**（游戏多用了几个第二卷的） |

> **结论：三线在第一卷范围内的视觉一致性是达标的。**
> 真正的缺口只有 B 类的 3 条 + 收尸人在游戏线的缺失。

## 六、建议

| # | 事项 | 优先级 | 成本 |
|---|---|---|---|
| 1 | **给 `29-LEVEL3` 补「视界呈现」一节**，写入收尸人与全城静止 | **高** | 低（纯文档） |
| 2 | **EP32 加「城主签字」视觉插入**，把跨服务幂等视觉化 | 中 | 低（一个镜头） |
| 3 | 漫剧第二卷补「熔断 / 缓存击穿」的视觉 | 中 | 中 |
| 4 | 小说第二卷补「消息队列」「服务调用链」的视觉 | 低 | 中 |
| 5 | 保留 A 类 13 条——它们是后续卷的资产，**不要删** | — | — |

## 七、可重跑的校验

```powershell
powershell -ExecutionPolicy Bypass -File tools/audit-cross-line.ps1
```

**后续任何一卷完成后，都应重跑此脚本**，检查新内容是否用上了对应卷的映射条目。

**判据**：如果某一卷的核心技术点在三条线里都找不到视觉映射，说明**设定集的 §3 需要补充新条目**。
