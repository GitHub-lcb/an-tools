## 0. 设计目标

### 0.1 LEVEL 3 要验证什么

LEVEL 1 教"时间会用完"，LEVEL 2 教"你救错地方会死得更快"。

**LEVEL 3 要教一件前两关都教不了的事：**

> **不是所有故障都一直在。**
> **聪明的工程师会等。**

### 0.2 相对前两关的关键差异

| 项 | LEVEL 1 | LEVEL 2 | LEVEL 3 |
|---|---|---|---|
| 故障形态 | 持续 | 持续且恶化 | **间歇性（有节奏）** |
| 失败线 | 时限 | 时限 + 数据库 | 时限 + **堆内存** |
| 核心新机制 | 重启陷阱 | 扩容反向 | **平静期 / 卡顿期** |
| 时限 | 15 分钟 | 40 分钟 | **60 分钟** |
| 视界带宽 | 3 | 3 | 3 |
| 主修手段 | 改代码发版 | 预热 + 发版 | **删除大对象 + 发版** |

## 2. 核心机制：平静期与卡顿期

### 2.1 时间结构

```
周期 0:  [0, 3)  卡顿    [3, 10)  平静
周期 1:  [10, 13) 卡顿   [13, 20) 平静
周期 2:  [20, 23) 卡顿   [23, 30) 平静
周期 3:  [30, 33) 卡顿   [33, 40) 平静
周期 4:  [40, 43) 卡顿   [43, 50) 平静
周期 5:  [50, 53) 卡顿   [53, 60) 平静
```

```javascript
function isStall(t) {
  return (t % CYCLE_LENGTH) < STALL_DURATION;
}
function severityAt(t) {
  return isStall(t) ? STALL_SEVERITY : CALM_SEVERITY;
}
```

### 2.2 卡顿期的惩罚

| 行为 | 平静期 | 卡顿期 |
|---|---|---|
| **诊断卡** | 正常时间成本 | **时间成本 × 2** |
| **修复卡** | 可用 | **不可用（按钮置灰）** |
| **看 GC 日志** | 可用 | ✅ **唯一不受惩罚的诊断卡** |
| **重启服务** | 可用 | 可用 |
| **同步进展 / 向上汇报** | 可用 | 可用 |

> **「看 GC 日志」在卡顿期不受惩罚**，因为 GC 日志是异步落盘的，不依赖系统响应。

### 2.3 玩家的时间账

一局 60 分钟 = 6 个周期 = **18 分钟卡顿 + 42 分钟平静**。

**修复卡（改代码发版，8 分钟）只能在平静期执行。** 而平静期最长只有 7 分钟——**跨周期的发版是允许的，但会在中途撞上卡顿期**。

```javascript
// 发版跨越卡顿期时：时间正常推进，但玩家会看到 Impact 在那 3 分钟里加速
```

**这是本关最核心的张力**：你必须在平静期开始发版，然后**熬过中间那 3 分钟**。

## 3. 双计量模型

### 3.1 Impact

```
impact += severityAt(t) × mitigationFactor × Δt
```

| 阶段 | 强度 | 说明 |
|---|---|---|
| 卡顿期 | **4.0** /分 | 全站响应超时 |
| 平静期 | **0.3** /分 | 少量残留影响 |

### 3.2 堆内存

```
每个卡顿期结束时：heapUsage += heapGrowthRate × (1.5 ^ restartCount)
```

**注意**：堆内存**只在卡顿期增长**——因为卡顿就是 Full GC 的表现，而 Full GC 说明堆快满了。

| 事件 | 效果 |
|---|---|
| 卡顿期结束 | `heapUsage += heapGrowthRate` |
| 使用重启 | `heapUsage = 60`，`heapGrowthRate ×= 1.5` |
| 删除大对象（修复） | `heapGrowthRate = 0`，停止增长 |
| `heapUsage >= 100` | **OOM → 立即失败** |

### 3.3 被动失败曲线

不操作的情况下：

| 周期 | 卡顿期数 | 累计 Impact | 堆内存 |
|---|---|---|---|
| 0 | 1 | 12 + 2.1 = 14.1 | 68 |
| 1 | 2 | 28.2 | 76 |
| 2 | 3 | 42.3 | 84 |
| 3 | 4 | 56.4 | 92 |
| 4 | 5 | 70.5 | **100 → OOM** |

**被动玩家在周期 4（约 t=43 分钟）触发 OOM。**

> **结论**：LEVEL 3 的被动失败是 **OOM**，不是超时。
> 这与 LEVEL 1（死于时间）、LEVEL 2（死于数据库）形成三级递进。

### 4.2 新增卡牌详解

#### `C_GC_LOG` · 看 GC 日志 ★

```javascript
effect: (s) => ({
  logKey: s.usedCards.get('C_GC_LOG') ? 'gc.second' : 'gc.first',
  effective: true
})
```

第一次使用返回：

```
Full GC 统计（最近一小时）：

  次数        47
  平均耗时     2.8 秒
  最长耗时     3.4 秒

  老年代占用：  92% → 96% → 94% → 97% …

Full GC 的间隔是规律的：**每 10 分钟一次**。
```

**这张卡是定位问题的钥匙，而且是卡顿期唯一能用的诊断卡。**

#### `C_HEAP_DUMP` · 导出堆快照 ★

```javascript
requires: (s) => s.evidence.has('E_GC'),   // 需先看 GC 日志
effect: () => ({ logKey: 'heap.dump', effective: true })
```

返回：

```
堆快照（占用最大的前 5 个对象）：

  1. java.util.HashMap         1.8 GB   ←
  2. byte[]                    120 MB
  3. com.xxx.OrderCache        86 MB
  ...

第 1 个对象的引用链：

  OrderCacheService.staticCache
    └─ HashMap
         └─ 2,847,392 个 Entry
```

**这一条线索指向根因。**

#### `C_CACHE_SCAN` · 扫描缓存对象 ★★ 正解前置

```javascript
requires: (s) => s.evidence.has('E_HEAP'),
effect: (s) => {
  s.bigObjectFound = true;
  s.rootCauseConfirmed = true;
  return { logKey: 'cache.found', effective: true };
}
```

返回：

```
静态缓存 OrderCacheService.staticCache

  条目数：      2,847,392
  最早写入：    2021-06-14
  过期策略：    **无**
  清理逻辑：    **无**

这个 Map 从服务启动那天起就在。
三年了。

它里面的东西，一条都没有被清理过。
```

#### `C_GC_TUNE` · 调大堆内存 ⚠️ 饮鸩止渴

```javascript
effect: (s) => {
  s.heapGrowthRate *= 0.7;      // 增长变慢
  s.heapUsage = Math.max(0, s.heapUsage - 15);  // 暂时回落
  return { logKey: 'gc_tune.on', effective: false };  // 永远不计有效
}
```

**看起来是正解**——调大堆内存，Full GC 频率下降，卡顿减少。

**但它是治标**：泄漏还在，只是被推迟了。而且堆越大，一次 Full GC 的 STW 时间越长——**卡顿会变少，但每次更久**。

> **设计意图**：这是本关的"扩容陷阱"对应物。LEVEL 2 用扩容教"救错地方会更快死"，LEVEL 3 用调大堆教"**缓解不等于解决，而且缓解本身有代价**"。

#### `C_SCALE` · 扩容 —— **本关首次有效**

```javascript
effect: (s) => {
  s.scaleCount += 1;
  s.mitigationFactor *= 0.7;
  return { logKey: 'scale.effective', effective: true };
}
```

**为什么本关有效**：瓶颈在应用层（GC 停顿），不在下游。**更多实例 = 每个实例的堆压力更小 = Full GC 频率下降**。

> **这是三关的对照设计**：
> - LEVEL 1：扩容无效（浪费时间）
> - LEVEL 2：扩容**反向**（加速崩溃）
> - LEVEL 3：扩容**有效**（瓶颈真的在应用层）
>
> **同一张卡，三种结果。教的是同一件事：扩容只解决"自己不够用"的问题。**

#### `C_RESTART` · 重启服务 ⚠️ 暂时有效

```javascript
effect: (s) => {
  s.restartCount += 1;
  s.heapUsage = HEAP_AFTER_RESTART;         // 回落到 60
  s.heapGrowthRate *= RESTART_GROWTH_MULT;  // 但增长 ×1.5
  s.evidence.clear();
  s.rootCauseConfirmed = false;
  s.evidenceLost = true;
  return { logKey: 'restart.temporary', effective: false };
}
```

**本关的重启是"看起来真的有用"的**：堆内存从 92% 回落到 60%，卡顿立刻消失。

**但**：
1. 泄漏速度 ×1.5
2. 证据清空（与 LEVEL 1、2 一致）
3. **最狠的一点**：重启后大对象会被**重新加载**，而且加载过程本身会让堆增长更快

复盘 · 间歇性故障的处理原则

不是所有故障都一直在。

有的故障有节奏：来一阵，走一阵，再来一阵。

处理这类故障，有三条原则：

  1. **不要在故障发作时抢救**
     系统响应慢，你的命令发不出去，诊断卡时间翻倍

  2. **在平静期做诊断**
     那是系统唯一"听得见你说话"的时候

  3. **算清楚下一次发作的时间，再决定什么时候动手**
     发版要 8 分钟。下一个卡顿期什么时候来？

**「等」是一个决策，不是一个放弃。**

## 7. 数值验算

### 7.1 被动失败

| 周期 | 时刻 | 卡顿期数 | Impact 增量 | 累计 Impact | 堆内存 |
|---|---|---|---|---|---|
| 0 | 0–10 | 1 | 12 + 2.1 | 14.1 | 68 |
| 1 | 10–20 | 2 | 12 + 2.1 | 28.2 | 76 |
| 2 | 20–30 | 3 | 12 + 2.1 | 42.3 | 84 |
| 3 | 30–40 | 4 | 12 + 2.1 | 56.4 | 92 |
| 4 | 40–43 | 5 | 12 | 68.4 | **100 → OOM** |

**被动玩家在 t ≈ 43 分钟 OOM。**

### 7.2 路径验算

**路径 A（标准解）**：

```
t=0:00–0:02  卡顿  4.0 × 2 = 8.0        → 8.0
t=0:02–0:03  卡顿  4.0 × 1 = 4.0        → 12.0  （跳过）
t=0:03–0:07  平静  0.3 × 4 = 1.2        → 13.2  （堆 +8 → 68）
t=0:07–0:10  平静  0.3 × 3 = 0.9        → 14.1
t=0:10–0:13  卡顿  4.0 × 3 = 12.0       → 26.1  （堆 +8 → 76）
t=0:13–0:20  平静  0.3 × 7 = 2.1        → 28.2
t=0:20–0:23  卡顿  4.0 × 3 = 12.0       → 40.2  （堆 +8 → 84）
t=0:23–0:30  平静  0.3 × 7 = 2.1        → 42.3
t=0:30–0:33  卡顿  4.0 × 3 = 12.0       → 54.3  （堆 +8 → 92）
t=0:33–0:38  平静  0.3 × 5 = 1.5        → 55.8
```

**最终 Impact ≈ 55.8，堆内存 92，t = 38 分钟。**

> **修正**：§5.1 表格中的路径 A 数值为粗算。**以实现时的数值积分为准**，本文档的逐段验算（55.8）是准确值。评级仍为 **A**（< 75）。

## 8. 三关对照总表

| 维度 | LEVEL 1 | LEVEL 2 | LEVEL 3 |
|---|---|---|---|
| **故障** | 重复下单 | 缓存雪崩 | Full GC 停顿 |
| **主失败因** | 时间 | 数据库 | **堆内存** |
| **核心教学** | 时间会用完 | 救错地方会更快死 | **不是所有故障都一直在** |
| **扩容** | 无效 | **反向** | **有效** |
| **重启** | 清空 Impact，毁证据 | 不清空，制造惊群 | **暂时有效，加速泄漏** |
| **时限** | 15 分 | 40 分 | 60 分 |
| **Impact 阈值** | 100 | 200 | 150 |
| **评级 S** | < 25 | < 40 | < 30 |
| **评级 A** | < 50 | < 90 | < 75 |

**三关合起来，教会玩家一件事：**

> **每一次事故都不一样。**
> **你学过的每一张卡，都可能在这一关失效、反向、或者刚刚好。**
>
> **唯一能带走的，是判断力。**
